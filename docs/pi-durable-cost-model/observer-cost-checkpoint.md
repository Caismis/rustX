# Observer cost checkpoint

This is a source audit of the retained production profile, not a new timing result. The complete profile and count evidence are in [final-production-profile.md](final-production-profile.md); the independently measured query-plan change is in [query-plan-results.md](query-plan-results.md).

The fair HTTP/SSE benchmark exercises different native observation surfaces. rustX's conformance `Driver::start_in` consumes production App notifications throughout execution. Pi's driver uses native submission settlement, native context capture and reopened-context verification, but does not mount `ConversationViews` or call `watchEvents`. Both use the same local provider and verify complete ordered requests and results. This supports the reported native-workload comparison, but does not isolate equal UI subscription work. Pi's separate coding-agent AgentSession/JSONL TUI is not this SQLite Harness benchmark.

At pinned Pi revision `90d863f7c1183b965f099855715d6e88c7b8a52c`, `ConversationViews.attach` hydrates a mount on the serialized Session line. Its detach callback deletes the mount after the last observer. The commit observer advances only mounted conversations from committed entry/document changes. A later observer rebuilds its initial snapshot from committed storage. This is a concrete architecture to compare; no artificial work or matching delay should be added to either engine.

rustX's `Host::ensure_worker` reads derived domains when a dependency cut is dirty and publication permits it. Its admission does not check subscriber count. `ReadDomainCut::read` includes transcript decoration, occupancy and a bounded trace page. Native publication also retains a bounded replay ring; subscribers are cursors into that ring, and an expired cursor fails explicitly with `resync_required`. Consequently, zero currently registered subscribers alone does not prove there is no disconnected client entitled to resume from a retained cursor. A subscriber-aware change must preserve late checkpoint snapshots, exact serviceable replay and independent Source lifetime. Skipping derived work on subscriber count alone is not yet a validated implementation.

Ordinary tool expansion and reasoning visibility are client-local. They do not explain all Source construction cost. The separate instrumented short-turn run counted 11 eagerly constructed Sources per turn: eight event envelopes, two raw message fragments and one request scalar. The scalar reached about 12–13 KiB and used a temporary SQLite navigation index despite fitting the resident byte carrier. The next candidate compactly stores bounded navigation coordinates, admitting up to 16 KiB without that connection/file; large Sources retain their bounded disk-backed path. This targets preparation for optional deep inspection without removing inspection or changing publication cadence.

In the existing short-small CPU profile, disjoint ownership groups contain 139/617 signals in publication encoding, 153/617 in read domains and 60/617 in notification consumption/relay. Source navigation contains 26/617 on a separate operation partition; these axes must not be added. Those signals neither attribute the entire gap to UI nor establish that all preparation is required by durability. They identify concrete always-on consumers and optional inspection preparation to reduce. No new Pi parity claim is made, and the large-case CPU increase in the query-plan stage remains visible.
