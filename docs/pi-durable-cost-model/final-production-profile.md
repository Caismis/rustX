## First isolated candidate

Fresh stacks include SQLite preparation inside row advancement, not merely explicit prepare calls. A minimal probe linked to the exact bundled rusqlite/SQLite reproduces 100 internal reprepares for 100 bindings of the indexed trace query. Replacing the closed kind with a literal still gives 100. Enabling SQLite QPSG gives zero in both cases. Probe sources/logs live in sibling `pi-parity-instrumentation`; an initial invocation omitted RUSTUP_HOME and failed before compilation, then used the environment's existing workspace toolchain.

[SQLite's configuration documentation](https://www.sqlite.org/c3ref/c_dbconfig_defensive.html#sqlitedbconfigenableqpsg) describes QPSG's bound-parameter-independent plan choice and possible cost of losing parameter-sensitive optimizations. Native finite read queries explicitly select their indexes. The candidate changes connection planning only; schema changes still invalidate statements. Existing physical-bound/query-plan tests, differential ordered results and all six benchmark cases must verify the tradeoff. No performance benefit is claimed from the microprobe alone.
