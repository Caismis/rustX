样本、请求与恢复的确切计数
- 3 次 round-robin rotations × 4 cases × 3 engines = 36 个 accepted 产品。每引擎 12 个。
- 每个 engine 主生命周期请求数为 3 × (40 + 96 + 1 + 1) = 414，不是 412。short-small 是 8 seed + 32 measured；short-large 是 64 seed + 32 measured；large 和 stream 各 1 measured。
- 每引擎 216 seed + 198 measured = 414。不能把全部 414 当成测量轮数。
- Rust/Pi 的 12 份比较文件合计覆盖 414 组有序请求；coreSemanticEqual=true。fullSemanticRequestEqual=false，原生 prompt/tool envelope 差异没有被宣称等价。Rust 与 Pi 各自 raw oracle 均 passed，并各自记录 40/96/1/1 条 reopened request。
- DeepSeek 的主生命周期同样是 414 次请求，另外 12 个产品各有一次 native resume 后验证续跑，故 DeepSeek provider 总数是 426。三引擎 provider 总数为 414 + 414 + 426 = 1254。
- DeepSeek 全部 12 次关闭与恢复验证通过：first/verification 进程均 exit 0，provider ok，记录中的请求数量与 raw 对齐；native_resume=true、unchanged_persisted_prefix=true。解码后前缀不变、seq 连续、session/end-seed 标记一致，SDK 后缀事件和恢复后新增 assistant 一致。每个产品保留一份非空原生 Zstd JSONL 文件。
- DeepSeek 原生日志事件数（每种 case 的三次重复相同）：short-small 328→338，short-large 776→786，large 16→26，stream 16→26。箭头前是首次关闭后，箭头后是恢复验证续跑后。
- 上述所有日志首次关闭时 request/header=1、request/context=1；恢复验证后 header=2、context=1。恢复会开始新 header，不能把它描述成严格只有变化才写。它展示了历史期间配置体积的避免重复，不证明其是时延主因。

结束边界与成本范围
1. Rust/Pi 的 wall 是 native durable settlement 加 live subscriber 完成；DeepSeek 的 wall 是 SDK session/wait idle，原生 JSONL 的最终 flush/fsync 可能尚未完成。DeepSeek 原生 200 ms batch、完整 SDK dispatch/pre-step checkpoint 配置均保留。
2. DeepSeek 关闭时会走原生 drain，关闭后可读日志和 resume 验证证明内容保留；SDK dispose 用 Promise.allSettled，exit 0 可能吞掉 root disposal 的失败，因此 fsync_success_acknowledged=false。它不是断电测试或 fsync 成功的正向凭证。
3. DeepSeek 首次 CLI 关闭额外 wall ms 的中位数 [范围]：short-small 46.210 [45.830,46.739]；short-large 47.648 [47.275,52.264]；large 55.205 [55.107,55.749]；stream 55.302 [55.288,60.948]。这段涵盖关闭请求至实际退出；不应简单均摊回单轮并声称持久性等价。
4. DeepSeek 保留原生 system/context/25 tools；Rust 7 tools、Pi 4 tools。DeepSeek 的首次 prompt/reminder 合并等原生差异明确记录；静态 envelope 来自经审阅的首次捕获，不是独立编写的规范，因此不能声称三者完整请求等价。
5. DeepSeek SDK 输出 committed session.event 和 status，不转发逐 token 的 partial 文本快照；内部消费了全部 128 个流式 chunks。Rust/Pi live subscriber 会消费 partial views。stream 含 128 × 10 ms fixture 节奏等待，约 1.6 秒 wall 不能解读成纯计算耗时。
6. Rust/Pi CPU 含产品进程及进程内 benchmark driver；DeepSeek 是直接 CLI 进程树和已 wait 子进程 CPU，外部 Python controller/provider 不计入。DeepSeek 过程样本均只观察到一个进程。main-thread children 遍历不保证任意线程创建的全部后代覆盖；已退出后代的 I/O 不可完整回收，writes 是进程计数而非物理设备写入量。
7. DSH source CLI/tsx 冷启动、完整关闭和额外恢复续跑保留为独立 lifecycle；不能把不等工作量的完整 lifecycle 相互排名。仅这 4 种 case 有 DeepSeek 支持；tool/cancel 仍明确 unsupported。

可从本组结果得出的性能观察
- rustX D 的两个短轮场景 native API 平均轮延迟中位数约 45–50 ms，Pi 约 4 ms，DeepSeek SDK idle 约 15 ms；原生边界差异必须随数字一起展示。
- 大输出场景 D 的 wall/CPU 绝对值低于两种原生参考；流式 wall 接近 fixture 等待下限，不能用接近的 wall 掩盖 CPU/writes 的差异。
- DeepSeek 在这个 API 窗口中进程 writes 很小，但 sampled PSS 最大；其 batch/final-flush 边界和 partial publication 工作量不同，不能把小 writes 直接解释成同等持久功能的效率倍数。
- 配置/工具定义增量记录、避免历史重复配置的原生模式值得继续验证；应保留 rustX 的逐历史请求检索语义，并分别测量捕获、持久写、字段索引与读取。固定 header 次数本身不是已证实的延迟因果结论。
