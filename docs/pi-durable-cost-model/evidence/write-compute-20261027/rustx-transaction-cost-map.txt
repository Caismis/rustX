2. The apparent readiness double write is not two transactions for ready and direct.
observation_readiness.rs:6 inserts a ready=0 row for each publication-requiring native J, then clears the events missing-evidence bit. mark_direct:54 calls mark:33 (UPDATE ready=1 where 0) and UPDATE direct=1. Both updates are inside the same post-fold transaction. Replacing the two SQL statements with one could save statement execution, but does not promise a WAL page/commit reduction because dirty pages coalesce within a transaction. It is intentionally not part of the current candidate.

The observed 416 frames in each of event_observation_readiness and its holes index can be explained exactly at this cohort grain: per turn five native transactions carry the eight J inserts (adoption, attempt, turn, request, final-four), then eight readiness transactions release them = 13 writes/page/turn * 32. This does NOT mean 13 INSERT events, 13 readiness commits or 26 commits. Transcript readiness is four writes/page/turn (accept insert, accept release, final C insert, final C release) = 128 frames; adoption reuses the already-published inbound T identity. sqlite page owner counts are page-write counts, not SQL statement counts, and endpoint dbstat cannot exclude intermediate page reuse.

Readiness-only commits account for 20 WAL frames/turn (640 total), ~6.0% of small 10722 and ~5.4% of large 11748 WAL frames. Removing all of them is not safe and would not remove most current WAL byte cost. Their CPU/commit overhead may still matter; no timing attribution is claimed from page counts.

3. Concrete future structural reduction, not implemented: one final-family readiness release.
The strongest bounded next opportunity is the four post-final releases at slots 13..16. The native facts are already one transaction and their ordered receipts are already returned together as CommittedModelTurn. An explicit final-family observer boundary could install provider -> canonical -> turn -> attempt CPU folds in existing order, then release only that exact family's J/T members in one readiness transaction and wake once. On this cohort its upper-bound commit reduction is 3 (16 -> 13), not five, and readiness WAL reduction is 6 frames/turn (10 -> 4 for the final family); original native fact and index writes remain.
This requires proving how the projection records each intermediate receipt/cut before final source release; it is not sufficient to call mark_native_observation_ready earlier or to pass a numeric min/max spanning unrelated events. The implementation must explicitly handle optional tool boundary (no turn/attempt terminal), pending adoption branch, observer missing/CPU fold failure, interleaved foreign-owner holes, independent WAL readers, old selected cuts, exact direct evidence, and recovery. It must retain immutable historical cuts even if physical visibility is released together. Existing native_readiness_tests.rs verifies one-batch atomic commit, no pre-commit visibility, failure rollback/reopen, foreign-hole preservation and terminal transcript independence; a family change needs analogous multi-batch tests plus failure after each CPU fold. A stronger all-or-none release on a failed final family must be an intentional contract decision, since the current implementation may already release the earlier provider event before a later observation failure.
No arbitrary queue/timer batching across owner callbacks is proposed. AttemptStarted, TurnStarted, inbound acceptance/adoption and request start currently separate cancellation, validation, ownership and recovery boundaries. No evidence here proves those can be eliminated while preserving functionality. In-memory-only readiness would require a separate multi-reader/ownership/recovery design and is not an authorized shortcut.

4. SQL/JSON work inside the native transactions is materially larger than the commit count.
persist_event_tx_internal sqlite.rs:11231 validates source identity/reference/lifecycle, probes sequence, writes lifecycle state when required, serializes full event_json and INSERTs events. It then derives separately recoverable observation families under optional_display_layout SAVEPOINTs (:21509): readiness, Statistics/Members, Execution, request terminal occupancy, event witness, Trace, bounded observation_json, Turn layout, and final receipt metadata. Only families required by the specific event run. A failure in one optional layout does not erase the native fact or another independently successful layout; merging these savepoints indiscriminately would change failure semantics.
The actual State persisted layout is only required for compaction/Goal at sqlite.rs:11389 and observation_state.rs:173 (todo changes on tool results elsewhere). Ordinary plain-text turns do not rewrite Goal/Todo/context State JSON. RuntimeClient State projection CPU is not a hidden state-file write.
- Statistics observation_statistics.rs:208 reads/folds bounded aggregate JSON and seals applicable new event versions.
- Execution observation_execution.rs:99 reads/folds a bounded summary. The frozen candidate at :198 now reuses the bytes returned by the successful bound check, removing the immediate second serialization. It preserves trimming, timing and SQL values, saves no commit by itself, and has not been timed yet.
- Event sequence UPDATE sqlite.rs:11434 occurs once per J fact including four times in final. These updates hit one shared transaction/page in final; reducing statement count is not equivalent to reducing four WAL frames or commits. Intermediate validation/receipt reads currently depend on the transaction-visible sequence.
- Native request/root trees are already incremental; saved nodes are reused. Current request scalar capture still derives and hashes fields/bytes before deduplicating page INSERTs. The other agent's bounded-length candidate owns that separate CPU path. Do not repeat rejected E's unindexed Original reader tradeoff or C's statement-cache experiment.
- version/epoch checks (manifest.rs:492) read rootpage and PRAGMA data_version/schema_version; they are not version-table writes.
- A second observation::index_message remains in sqlite.rs:6144 rebind_canonical_display after initial canonical indexing. Raw Tool args require rebinding, and the optional second indexing currently can repair an earlier derived-layout failure. A text-only removal needs a success proof or reordered indexing and failure tests; it has not been made in this candidate.

5. What the frozen final-settlement candidate actually removes.
Normal public stage_publication_frames retains the existing native frame rows, live content indexes and readable receipts. Only frames consumed immediately by the same final transaction bypass transient publication_frames INSERT, live content/block/frontier derivation and discarded frame receipts. The original path would delete those frames/live rows before this transaction committed, so no successful intermediate visibility is removed. Sequence/message/stream/proposal ownership validation and P -> U -> C remain. Raw tool suffixes still become mandatory canonical raw bytes: existing live prefix when healthy, retained original frames on optional-live-index failure, then exact final suffix bytes; no JSON reserialization of those raw bytes. All mandatory errors roll back the outer final transaction. Text/tool reopening and injected failure tests have been added, but root owns their execution. This candidate saves no commits directly; its actual WAL/CPU benefit must be measured after correctness passes.

6. Pi comparison constraints.
Pi pinned 90d863f uses WAL/NORMAL too, with five semantic transactions on the same short stable case. Its task record/checkpoint is overwritten at final; it does not preserve rustX's complete historical request/config inspection catalog. Pi stable tool/system data are incremental entries. See sibling pi-transaction-cost-map.txt for exact five-call paths and 26 SQL runs/turn reconstruction; old Pi SQL counts are explicitly historical, fresh root WAL confirms five current commits/turn. Matching Pi durability does not authorize deleting rustX observation/read-cut functionality. The present candidates remove duplicate or unobservable work while keeping those semantics; neither claims general feature-equivalent parity from the five-commit target.
