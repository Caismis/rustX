一、代码事实：DeepSeek 的“只变化时追加”有哪些准确边界

1. request/header 并非无条件只在变化时追加。
  packages/core/agent-loop/src/agent.ts:615-651 的 buildRequest：
  - 每个 loop 实例第一次 requestHeaderLogged=false 时必追加；无历史为 reason=initial，有历史为 reason=resume（635-642）。
  - 后续 config/adapterDefaults/tools 不等则 reason=change（643-648）。
  - 即使内容相等，startsRequestSeries 或 surface.contentGeneration 改变也追加 reason=series（625、632-634、649-650）。
  - 只有同一 loop、无 series 边界且 header 相同的通常后续请求才跳过这条日志。
  工具增删还会生成绑定 headerSeq 的 developer/message（652-665）；不能丢失历史工具定义再靠“当前工具表”重建旧请求。

2. request/context 确实只在四个比较字段变化时追加。
  packages/core/agent-loop/src/agent.ts:669-683：provider、model、contextWindow、systemPromptUpdate；首次无 previousContext 也追加。
  system prompt 本文不塞在 request/header：它通过 system/message 进入消息表面，随后和用户/助手历史一起 derive。

3. 省掉日志写入不等于省掉每步所有 header 成本。
  packages/core/session/src/request-header.ts:21-29 canonicalHeader；43-51 headerEquals：逐字段比较配置，按顺序比较工具。
  同文件:32-35 的 sameSchema 每次对两边 schema 执行 JSON.stringify；稳定的工具集合仍承担比较/序列化工作。
  packages/core/agent-loop/src/agent.ts:583-595 仍 clone/freeze request proposal 并执行 waterfall。
  packages/core/agent-loop/src/agent.ts:686-702 仍冻结 header，derive messages，再组装 request。

4. 增量投影与历史重建有明确边界。
  packages/core/session/src/index.ts:899-940：header/context fold 各有已消费位置，仅折叠新增事件。
  同文件:943-956：工具历史也增量折叠。
  同文件:959-1004：消息纯尾部增长只投影新节点；contentGeneration 改变时重建。
  每次返回 [...derived]（1004），所以仍有 O(history) 的新数组复制；不是请求组装与历史长度无关。
  packages/core/session/src/request-header.ts:54-68 支持按历史前缀取最新 header。
  packages/core/agent-loop/tests/request-reconstruction.spec.ts:1-5、84-124 是已有源码测试的重建/稳定性约束；本次只阅读，没有运行它。
  这证明其设计意图是“历史日志 + 当时配置 + 有序消息表面可重建请求语义”，不是让旧请求使用当前配置。
  它本身不等于 rustX 的任意原始字节范围、字段 Fact、proof/hash 与独立 read-cut 契约。

三、持久性成本仍存在，不能把 SDK idle 当作等价已落盘

  packages/core/session/src/index.ts:761-825：append 同步 snapshot/validate/deepFreeze 与发布；持久插件异步缓冲。
  packages/session/session-persistence-jsonl/src/storage.ts:36、274-313：200 ms 上限，live event 再 structuredClone，批量 drain。
  packages/session/session-persistence-jsonl/src/index.ts:1388-1391、1411-1438：batch 编码/Zstd，再 open、writeFile、sync、close；不是只写内存。
  packages/session/session-checkpoint-policy/src/index.ts:29-36、63-81：模型 dispatch 之前、顶层工具 dispatch 之前、pre-step await flush；
    后续边界会覆盖前轮结果，但 SDK idle 不是 final flush/fsync acknowledgement。
  所以本观察不能支持“去掉一条 header 就解释了整个三引擎时延差”，也不能拿 idle latency 做相同持久性速度比。

五、未来推断：1-2 个可证伪方向，不是已证明的收益

方向 A：把稳定的配置与工具定义作为不可变共享片段，并让每次 RequestSnapshot/Source 绑定其当时的片段。
  启发来自 DeepSeek header epoch，而不是省略旧请求记录。每请求 identity/contributions/selected-input 仍独立保存；
  配置/工具/系统提示改变、resume、retry、compaction 的边界都必须绑定准确的旧版本。
  优先复用现有 authenticated page/template/root 机制；先测 SourceScalar 中构造/校验/哈希各占多少，而不是引入新缓存后再猜效果。
  可验证结果：相同工具配置 8/64 history 下，逐请求 capture byte visits / encoded Fact bytes / hash bytes / SQL 次数是否下降；
  交替改变同名工具 schema、系统提示、模型参数、retry/compaction 后，live 和 reopen 的全部历史请求、原始字节页、字段路径/顺序仍一致。
  只按 tool name 或可变 registry identity 缓存不够；重复配置碰巧有相同 JSON 也不能替代历史 immutable binding。
  风险：片段拼接需维持既有精确编码与字段几何，可能增加 Reader 路由与哈希校验成本；未测前不能承诺收益。

方向 B：先独立验证 E 的 bounded Original / 延迟 Fact 构造这一已提出方案，再决定是否保留或扩大。
  DeepSeek 的事实日志与按需 fold 支持“原始事实先完整保存、派生视图消费时建立”的设计方向；它不直接证明 rustX 的 E 更快。
  分开量化写侧 SourceScalar / turn CPU / writes 和读侧 field/child/key-span/bytes pagination：未读、读一次、重复随机字段读取；
  覆盖 <16 KiB、恰好边界、>16 KiB、密集小字段、长字符串，以及无观察/late snapshot/live-subscriber 三种使用方式。
  不修改历史请求重建、原始值与字节、损坏页拒绝、事务 rollback/reopen 契约；如果只移动成本却显著恶化正常读侧，就不能据写侧数字宣布整体胜出。

结论边界
  已证实的模式是：变化驱动的 header/context 日志、按尾部增量投影、assistant stream 的紧凑最终事实；
  已观测的是上述事件数量和逻辑体积；尚未证明其分别贡献了多少毫秒。
  header 一直不变只是减少重复持久事实的证据，不是它成为三引擎时延主因的证据。
