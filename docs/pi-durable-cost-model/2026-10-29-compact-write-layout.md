## 完成的改造与功能边界

`events.observation_witness`、`events.observation_trace_fact`、`events.observation_members` 使用现有 rmp-serde 依赖生成 MessagePack。外层记录使用固定位置 tuple，内部结构仍使用 map 和 human-readable 序列化语义，保留枚举标签、可选字段、原生整数及嵌套 JSON 行为。canonical/proposal 等其他 Trace 记录仍保留原有 JSON 路径。

原公开 JSON 准入上限不变：一般记录 16,384 字节，普通 witness 初次写入 16,256 字节并预留 128 字节，最终附加后仍限 16,384 字节。私有物理上限为 **49,152 字节（48 KiB）**。不能直接用公开上限或其两倍限制 MessagePack：短十进制浮点数在 MessagePack 中可能占 9 字节，反过来会拒绝原本合法的记录。对当前封闭的 JSON 兼容类型，三倍界限覆盖这种展开，SQL CHECK 和 schema 校验使用相同界限。

writer 复用既有保守预算证明：确定通过时直接编码私有记录，省去随后丢弃的完整 JSON 长度遍历；确定超限仍拒绝，不确定时计算实际公开 JSON 长度。reader 先检查物理长度、array 根和 JSON 兼容形状，再按类型解码并验证实际公开 JSON 长度。形状扫描不分配容器，深度限制为 128，拒绝非有限浮点、binary/ext、非字符串 map key、恶意容器长度、截断和尾随字节。不能用 writer 的保守拒绝条件替代 reader 的实际长度检查，否则会缩小原有可读取范围。

终版改用 `from_read_ref` 直接读取借用字节，去掉初始 128 字节 scratch 分配和字符串中间复制。原 scratch 是可复用缓冲区，不能说原来每个字符串都新分配一次。EOF 检查使用不会递归进入容器的 `u8` 类型探针，只接受 `InvalidMarkerRead(UnexpectedEof)`；已覆盖所有 256 种尾随 marker 和所有数值 payload 截断位置。没有进行首批候选与终版之间的直接配对消融，不能认定这项修正解释了性能变化。

同一事务内的 typed witness 仍通过实际存储字节相等验证后复用，命中时不重新解码。正常事件 INSERT 已携带完整 transcript；独立失败路径中的 transcript 附加操作仍先读取实际记录，在同一事务内解码并带原字节条件更新，以保留触发器改写与独立回滚语义。

请求页升级为 `RXSP v2`：leaf 和 branch 的 key 保存 UTF-8 边界上的公共前缀长度与后缀，每页首 key 从零前缀开始。每页仍最多 64 项；实际存储大小和按旧完整 key 计算的展开大小均不超过 65,536 字节；key/value 上限仍为 4,160/40,960 字节。排序、末 key、哈希、树深度与历史 root 的独立可读性保留。Builder 增量维护存储/展开大小，flush 后重置，避免反复扫描整层 key。

SQLite 保持 **WAL/NORMAL**，schema **82 → 83**；按仓库要求不提供旧格式兼容解码或迁移。公开输出、字段分页定位、历史 cut、有界读取、原生恢复、各派生域的独立损坏处理与失败隔离均保持原有契约。

## 实际减少了什么写入

四个独立列诊断各测量 32 轮、256 个事件；以下是主库存储列的逻辑字节增量，包含三列的所有事件。它们不包含 TEMP、中间删除值、SQLite 页填充或 WAL 放大。

| 列或合计 | 8 历史：R → T 字节 | 64 历史：R → T 字节 |
|---|---:|---:|
| observation_witness | 137,637 → 66,042 | 137,856 → 66,784 |
| observation_trace_fact | 110,878 → 66,537 | 111,040 → 67,168 |
| observation_members | 42,428 → 26,582 | 42,592 → 26,880 |
| 三列合计 | 290,943 → 159,161（-45.295%） | 291,488 → 160,832（-44.824%） |
| 全部主库逻辑列 | 1,255,555 → 1,121,629（-10.667%） | 1,277,983 → 1,147,667（-10.197%） |
| request_source_pages，包括 hash | 158,440 → 156,393（-1.292%） | 150,624 → 150,944（+0.212%） |
| request_source_pages 行数 | 229 → 229 | 224 → 224 |

主要收益来自三个证据列。前缀编码自身多一个长度字段，重复前缀不足时可能增加字节；当前实际页分组下，导航页收益很小，长历史还增加 320 字节。不能将第二项宣称为显著的全局写入优化。

四个独立 WAL 诊断中，8 历史帧数 **6,318 → 6,210（-1.709%）**，64 历史 **7,244 → 7,108（-1.877%）**。两版均为 32 轮 **160 次主库写提交，即每轮 5 次**，本轮没有再次减少事务数量。

按端点页面归属映射，events 表帧数分别为 384 → 288、386 → 288；events 索引合计仍为 **1,858 / 2,139 帧**；request_source_pages 仍为 **98 / 96 帧**；content_segments 与 content_frontiers 合计分别为 869 → 870、1,191 → 1,173 帧。归属映射只是端点分类，不是每次写入时的严格表归因。

这解释了为何三列少约 45% 字节，累计进程写入却只少约 2%–4%：提交次数、主要索引维护和其他内容/状态表仍在，较短记录只有跨过页边界才减少部分页写入。逻辑字节、WAL 帧、累计进程 write_bytes、设备流量不能互换。完整进程写入仍为固定 Pi 的约 **4.145–4.630 倍**（热请求四格）。

## 延迟差距与证据限制

紧凑编码没有消除原生事实、可独立读取的派生域和其索引，也没有取消按当前状态生成公开 checkpoint、分页历史读取及损坏验证。读取缺少同事务 typed 证明的记录仍需解码和实际公开长度校验。这些是当前流程中实际执行的工作；本轮数据并不证明其全部成本都不可进一步降低。

独立 CPU 诊断包含三类场景的 baseline/终版各一组 profile 与无 profiler control。live 长历史 profile 中，publication encode 占 35/187 → 35/175 个 inclusive 样本，read_with_trace 为 23/187 → 21/175，request read-layout 建立为 20/187 → 15/175。它们会重叠，不能相加为总成本或直接变成预期加速比。采样频率 250 Hz，Tool 仅 10/11 个样本；零样本不等于零成本。

诊断 live 长历史 control 平均延迟从 17.482 降至 16.669 ms，方向与正式五对结果不同；无 live 长历史 control 从 15.422 增至 16.684 ms；Tool control 从 56.667 降至 40.677 ms，但 profile 从 38.944 增至 43.001 ms。这些单次诊断不能取代正式配对结果，也不能确证回退原因。删除 scratch/中间复制有源码依据，但没有证据证明它解决了整体性能差距。

正式数据中 `/proc` CPU 计数为 100 ticks/s，每个端点粒度 10 ms。测量窗口 CPU 包含轮次间计数/内存采样开销，单轮 settled 延迟在采样前记录。每格五对仅提供描述性中位数与范围；没有合并轮次、挑选有利样本或据此给出因果置信区间。

Pi Durable 固定为 `90d863f7c1183b965f099855715d6e88c7b8a52c`（`packages/durable`），DeepSeek Harness 固定为 `687f282e8625c6b8d11ff58211a90524be2e4317`。**本轮未重跑 Pi/DeepSeek**；旧批次 60 个 Pi、12 个 DeepSeek 产品和固定摘要哈希继续作为独立参考，比例是跨批次中位数比，不是本轮配对效果。

相对固定 DeepSeek，live short-small / short-large / stream / large 的平均延迟比为 **1.179 / 1.240 / 1.008 / 0.269**。DeepSeek SDK idle 不等待最终 flush/fsync，也没有相同的 partial-token 文本发布；退出/flush 的 wait4 CPU 独立保留，完整进程写入不可得，不能当零或构造同口径完整生命周期比。Rust/Pi 核心请求等价校验排除工具定义（7 对 4），功能集合并不相同。AppServer transport 改造也不在本次对齐的进程内基准中。
