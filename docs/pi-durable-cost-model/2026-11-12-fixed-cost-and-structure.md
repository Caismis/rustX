# 每轮固定成本与结构性改动（2026-11-12）

本文记录斜率压平之后的工作：冷恢复有界化、每轮固定成本、三项结构性改动，以及仍然存在的差距和它们对应的功能。所有计时均在空载机器上测得（i9-14900K，驱动、模拟模型服务、被测进程统一绑定 P 核 2 和 8，`benchmarks/runtime/turn-growth.py --affinity 2 8`）。参照产品用同样的绑定和同样的负载重跑（`benchmarks/runtime/reference-growth/run.py`）。

本分支没有与最新 `main` 对齐，对齐留给后续工作。

## 结论

- 随会话轮数增长的斜率是平的：CPU、内存、冷恢复都不随历史增长。
- 文本轮每轮约 8.4–9.4 ms CPU、约 8–9.5 ms 耗时；工具轮约 22–23 ms CPU、约 21–25 ms 耗时。
- 与 Pi Durable 相比，每轮固定 CPU 仍高一倍多。剩余部分分散在各个持久化与观察环节，没有单一热点，按功能列在"剩余代价"一节。
- 工作区是 git 仓库时，"本轮改动文件"卡片改为与 deepseek-harness 一致的会话级私有 index 快照。它让工具轮多等一次快照，这是该功能的代价。

## 做了什么

### 冷恢复有界化

附着冷会话的工作量不再随历史增长：恢复前沿随事件在同一事务中持久化；活动上下文在首次使用时才加载；待办、会话活动、子代理注册表改为索引读取。`cold_attach_work_does_not_grow_with_history` 锁住读取行数与 VM 步数（文本 64/512/2048 轮均为 77 行、1,389 步）。

代价（方案 A，已确认接受）：冷打开时只做有界校验，不再校验全部历史。

- 前沿之前的行若被离线破坏，只在被读到时发现。
- 活动上下文正文的损坏在首次使用时报告，而不是附着时。
- 外部进程改写身份数据不会被持久化的身份前沿发现。
- 索引漏掉整行子代理记录时无法发现。

另有两条既有边界未改变：恢复与压缩视图不对照原始 Surface 操作做认证；活动消息上限 8,192 条（`src/context/resources.rs`），未压缩的工具会话在 2,048 轮时已在上限上。

### 每轮固定成本（微优化）

- 传输编码：标签选择与十进制数字不再分配，堆分配减少约 70%，输出字节不变。
- 观察域读回：已被取代的读回在取得连接后直接放弃；没有新信号时不再排空 Journal。读事务每轮减少 57%（文本）和 69%（工具）。
- Journal 写路径：热语句全部走缓存，去掉只包一条语句的 savepoint 和只为防触发器的回读。每轮 SQL 执行 720→621（文本）、1,689→1,392（工具）。
- 会话目录写入不再重复创建目录。

### 结构性改动

1. **投影通知改为增量**（协议 78→79）。过渡只携带相对订阅者已持有状态的变化，以游标为基准；基准不匹配走原有重同步；新订阅者仍先取完整快照。每轮推送从约 194 KB 降到 32 KB（文本）、547 KB 降到 97 KB（工具）。网页控制台与 TUI 用 313 帧真实事件序列逐帧验证增量应用后的状态与全量折叠相等。
2. **`events` 表键列**（schema 112→113，无迁移）。13 个虚拟生成列统一稀疏索引的键；工具查找改走专用索引，不再按历史读取全部活动消息；请求几何复用同一依赖周期内已认证的长度。
3. **工作区变更快照与 deepseek-harness 一致**。见下节。

### 工作区变更（"本轮改动文件"卡片）

该功能只用于展示，不回退、不持久化、不进入模型输入。实现改为与 deepseek-harness 的 `workspace-changes` 包同一机制：

- 仓库定位每个运行时一次；不在任何仓库内的工作区不启动 git。
- 会话级私有 index（以用户 index 为种子）和私有对象目录跨轮复用，用户对象库以只读 alternate 挂接。未变化的文件靠 index 中的元数据跳过，内容不进服务端内存。用户仓库的 index、对象、ref、工作树不被修改。
- 每次快照两条 git 命令（`add --all --ignore-errors`、`write-tree`），共用一次沙箱监督调用；轮末一次 `diff-tree -r -M --numstat`。
- 文件工具编辑前后的整文件捕获覆盖 git 覆盖不到的路径。
- 超过 2 MiB 的文件不提供对比，标记为过大。

与此前行为的差异以 deepseek-harness 为准：轮次进行中用户自己的编辑算进该轮；尊重 skip-worktree 与稀疏检出；运行时启动之后才初始化的仓库需重开会话才被识别；历史对比依赖用户仓库的对象库；换行与编码按 git 内建规则规范化。

成本（空载）：

| 工作区 | 文本耗时 | 工具耗时 | 进程内存 |
|---|---:|---:|---:|
| 非 git 目录 | 8.9 ms | 24.8 ms | 约 91–96 MiB |
| git 仓库，1 个文件 | 10.8 ms | 45 ms | 约 91–98 MiB |
| git 仓库，5,265 个文件 | 22–31 ms | 56–84 ms | 约 84–91 MiB |

- 工具轮要等基线快照完成才执行工具，所以多出约 20 ms（小仓库）到 30–60 ms（大仓库）。文本轮的快照与模型调用并行。
- 轮次结算之后卡片记录完成还需要一段时间（小仓库约 18–25 ms，大仓库约 35–50 ms），期间会话尚未空闲。
- 基准在 git 工作区下报告的服务端 CPU（文本约 17–18 ms、工具约 38–45 ms）包含驱动程序在等待会话空闲时反复发出的 `thread/read` 查询。采样显示工作区变更自身的代码约占 1%，多出的 CPU 在处理这些查询上，不是产品每轮的成本。
- 被改动的大文件成本与文件大小成正比：一个 64 MiB 的文件每轮被改一次，每轮约 0.8 秒 CPU（主要在 git 子进程）、每个版本占用 64 MiB 临时磁盘，会话结束时清理。

曾经尝试过的进程内实现（gix，每轮把整个工作区读入内存）在 5,265 个文件的仓库上每个工具轮约 1 秒、2 GiB 内存，已删除。

## 剩余代价（按功能）

空载采样（gperftools 500 Hz，193–320 轮，非 git 工作区）。百分比是该调用路径占全部样本的比例，各行有重叠，不能相加；每 1% 约等于文本 0.09 ms、工具 0.23 ms。

| 功能或环节 | 调用路径 | 文本 | 工具 |
|---|---|---:|---:|
| 模型回合结算（Journal、规范内容、回执） | `settle_model_turn` | 16.3% | 16.6% |
| 模型回合开始与请求记录 | `commit_model_turn_start` | 14.4% | 12.2% |
| 精确历史请求（请求 Source 的增量索引） | `index_request_read_layouts` | 8.4% | 7.1% |
| 有界显示与回放游标（投影发布与计量） | `PublicationDraft::encode` | 14.0% | 14.1% |
| 其中检查点捕获 | `capture_checkpoint` | 9.2% | 9.3% |
| 独立观察域的读回与校验 | `observation_checkpoint_head` | 10.0% | 13.3% |
| 向客户端发送通知 | `enqueue_notification` | 6.6% | 6.0% |
| 入站消息采纳 | `adopt_pending_batch` | 6.4% | — |
| 工具执行阶段的事件与结果提交 | `execute_tools_staged` | — | 12.9% |

存储层的确定性计数（`turn_write_work_tests`，预热后一轮）：文本 621 条 SQL、20,413 VM 步、7 次提交、258 个 WAL 帧；工具 1,392 条、45,266 步、13 次提交、553 帧。`events` 表的 41 个索引不是主因：它们是稀疏索引，一个文本轮只新增 58 个索引条目，事件插入占 VM 步的 18%。写路径的工作量均摊在每个事件的观察域维护、回执与请求组装上。

每轮写入量（文本约 255 KiB、工具约 659 KiB）比 Pi Durable 高 12–14%，主要来自每轮的提交次数和 512 字节页上的根页重写。

没有做、可以继续做的两项：

- 检查点捕获按需进行（现在每次发布都捕获并计量，而它只在新订阅者接入或重放时需要）。
- 合并崩溃语义等价的相邻提交（文本 7 次、工具 13 次），需要逐处论证恢复等价。
